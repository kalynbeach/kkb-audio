# Authored MP3 conformance fixtures

Generated by `./node_modules/.bin/bun tools/generate-mp3-fixtures.ts` using
Bun 1.4.0, FFmpeg 9.0.1 and LAME 4.0. No copyrighted music, recordings,
physical output or network media. Signals are PCM16 sine waves, amplitude 0.1,
left/mono 440 Hz, right 659 Hz. CBR is 128 kbit/s; VBR is LAME `-V 2`.

The eight matrix files cover mono/stereo × 44100/48000 Hz × CBR/VBR.
0.137 seconds yields 6042 source frames at 44100 or 6576 at 48000.
`short` has exactly 17 stereo frames at 48000; `crc` has 6576 and LAME `-p`.

`vbri` is **constructed metadata**, not a claim about a Fraunhofer encoder:
the script replaces the first non-audio LAME Info frame with version-1 VBRI,
retains the original audio packets byte-for-byte, writes seven audio packets,
2688 audio bytes (excluding the 384-byte metadata frame) and a single scale-1
table entry of 2688. This byte origin follows current AndroidX `VbriSeeker.create`,
not an independently audited encoder specification. FFmpeg 9.0.1 skips this
metadata frame and outputs 8064 frames without recovered trim. Its f32 reference
is unchanged by the corrected byte-origin convention.

Native and built-Wasm tests construct a two-entry scale-5 table with four and
three audio packets per group, floor-quantized lengths 307 and 230. This checks
acceptance without demanding exact scaled-byte equality; it does not certify an
encoder's rounding convention. Other mutations set advisory byte/frame totals
and table values to zero, one or u32::MAX. All must retain the same finite PCM and
history-restoring seek output via the full scan fallback. Unsupported versions,
invalid structural fields/table extents and malformed audio still reject.
The ignored VBRI delay field is not promoted into an original-input timeline.

`.f32` files are FFmpeg-decoded interleaved little-endian float32 references,
not pre-encode PCM. Tests require exact frame counts and maximum absolute
sample difference <= **1e-5**; observed native maximum was 2.31e-7. Sequential
versus post-seek output from the same decoder/converter is **bit-identical**,
including resampler pre-roll. Neither tolerance is a listening-quality claim.
Malformed/missing/unsupported cases are explicit deterministic byte mutations
in source-named Rust/Wasm tests; fixtures never need installed encoders to test.

## #20 loop-history fixtures

`bun tools/generate-mp3-loop-fixtures.ts` uses the existing authored PCM16 fixture and LAME4.0, explicitly forcing MPEG-1 sample rate. `loop-crc-{44100,48000}-{1,2}.mp3` uses32kbit/s CRC with mono or ordinary stereo. These small frames contain no Info/Xing packet: validated media lengths are46080 at44100 and49536 at48000, without recovered trim. The48000-stereo minimum main-data payload is58bytes. `loop-dual-48000-2.mp3` uses128kbit/s dual-channel (`-m d`), also from the authored one-second source. These exercise the unchanged strict inspector and bounded restoration paths, not pre-encode PCM equality. No audible output or new encoder compatibility claim.
